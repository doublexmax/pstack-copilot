### Shipping

**You own what lands. Verify each PR independently, land only the verified run from the root, then sequence the merges one at a time.** For "land the chain", "ship it", "enable auto-complete", or the second half of a chain that **Babysit** already drove to green.

This is the half after `playbooks/babysit.md`. Babysit makes a chain mergeable. Shipping decides what is actually safe to merge and then lands it. Green is not safe, and the gap between those two words is where this playbook lives. ADO mechanics live in `../references/ado.md`; read it before step 4.

1. **Verify every PR independently before arming anything.** One subagent per PR, not batched, each exercising the real surface against parent versus head — the project's own `.github/skills/verify-*` skill if it has one, otherwise `principle-prove-it-works` applied to whatever the change actually touches. Each returns `PASS`, `PASS+NOTES` or `FAIL` and posts that verdict on its own PR so the record outlives the chat. Safe means a verdict from an agent that did not write the code. CI green is not a verdict, and an approving bot review is not a verdict.
2. **Land only the contiguous verified run rooted at the bottom.** Walk up from the lowest unmerged PR and stop at the first one without a passing verdict, where both `PASS` and `PASS+NOTES` pass. A verified PR sitting above an unverified one is not landable, because merging it would pull the gap in underneath it. Report the ceiling as a PR number and say what breaks the chain.
3. **Re-check that the verdicts still describe the code.** A rebase rewrites every SHA above it and silently invalidates every verdict without touching a single check. Compare `git patch-id` at the verdict SHA against the current head before trusting an older verdict, and re-verify anything that actually drifted. Twenty-one verdicts went stale this way in one run with no signal at all.
4. **Arm auto-complete on the frontier PR only.** The frontier is the lowest unmerged PR, the one targeting `master`. Arm it with `repo_pull_request_write action=update autoComplete=true`, setting `mergeStrategy` and `transitionWorkItems` as the repo expects. Then confirm: re-read the PR and check `autoCompleteSetBy` is populated. Unlike GitHub's `autoMergeRequest`, ADO sets this the instant you arm, so an empty reading means it genuinely did not arm.
5. **Never arm auto-complete on a child PR.** Only the frontier targets protected `master`. Every child targets its unprotected parent branch, where typically *no* policies apply, so ADO completes it immediately and collapses the chain into itself. There is no merge queue to sequence this for you. If a previous agent armed one, disarm it with `repo_pull_request_write action=update autoComplete=false` and confirm `autoCompleteSetBy` is empty again.
6. **Never complete a parent with `deleteSourceBranch` on while it still has children.** The children target `refs/heads/<parent>`; deleting that ref orphans every PR above it. Set `deleteSourceBranch: false` in `completionOptions` for any PR with something stacked on it, and clean the branches up after the chain has fully landed.
7. **You are the sequencer, because ADO is not.** Nothing retargets children when a parent completes — the child keeps pointing at a branch that may no longer exist. So the drain is a loop you run, one PR at a time: arm the frontier, wait for it to complete, retarget the next PR onto `master` with `repo_pull_request_write action=update targetRefName=refs/heads/master`, verify its `mergeStatus` re-evaluated, arm it, repeat. One PR armed at a time, no exceptions. A second armed PR is how a chain merges out of order.
8. **Watch the drain, do not thrash it.** Poll the frontier under autopilot mode on the cadence in the reference until the ceiling is reached. `ADVANCE` is progress, not termination. Do not rebase, force-push, or push speculatively while a PR is mid-complete. Report each merge and the new ceiling. If the drain stalls, diagnose from the policy list before mutating anything, because a stalled policy and a broken chain look identical from the outside.
9. **Stop at the ceiling.** When the verified run is merged, report what landed, what the next unverified PR is, and what verifying it would take. Extending the run is a new pass through step 1, not a judgment call you make at 3am.

**Reply:** the verified run and its ceiling, each PR's verdict and who produced it, what you armed and how you confirmed it, what landed, and what the next gap needs.
